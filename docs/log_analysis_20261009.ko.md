# 2026-10-09 운영 로그 분석

분석일: 2026-10-10. 대상: `log.out.bak`(약 174 MiB). HTTP access log에 기록된 시간 범위는 2026-10-09 09:10:05 ~ 2026-10-10 06:55:02, 약 21시간 45분이다. 로그 시각 표기를 그대로 사용했다. 코드와 로그를 읽어 분석했으며 운영 서버·DB에 접속하거나 배포하지 않았다.

## 판단

반복 상태 조회와 WebSocket 연결 시도가 많다. HTTP 성공 응답은 대체로 빠르게 처리돼 서버 전체가 지속적으로 과부하였다는 증거는 없다. CPU·메모리·DB/Redis 지표가 없어 처리 여유를 확정할 수는 없다. 사용자가 약 140명이라는 수치는 이 access log만으로 검증할 수 없으며, IP 수·연결 수는 사용자 수 또는 동시 접속자 수와 다르다.

## 오류

### 종료된 WebSocket으로 전송: 27건

모두 다음 RuntimeError다.

```text
Unexpected ASGI message 'websocket.send', after sending 'websocket.close' or response already completed.
```

운영 코드 traceback 기준 24건은 `chat_v3/websocket.py:186`의 `online_users_updated` 전송에서, 3건은 15분 재인증용 `SESSION_REFRESH_REQUIRED` 전송에서 발생했다. 채팅 WS에서 종료 감지와 전송이 겹치는 상황이다. 현재 최상위 처리에는 WebSocketDisconnect 처리만 있고 전송 중 RuntimeError의 정상 종료 처리는 없어 traceback으로 남는다. 오류 27건 자체는 전체 53,806회 채팅 연결 시도의 반복 원인을 설명하지 못한다.

백엔드 수정 방향은 채팅 V3 전송 경로에서 실제 종료에 해당하는 RuntimeError를 WebSocketDisconnect로 처리하고 연결 정리를 수행하는 것이다. 다른 프로그래밍 RuntimeError까지 일괄 숨기지 않는다. 종료 직후 접속자 갱신과 재인증 전송을 시도하는 경우를 회귀 검증한다.

### HTTP 401: 30,031건

초대 알림 14,983건, 제재 조회 14,979건으로 두 경로에 거의 집중된다. 인증이 거절되는 동안 두 상태 조회가 반복된 패턴이다. 로그에 응답 본문이 없어 토큰 만료·잘못된 토큰·인증 헤더 부재 중 어느 것인지는 확정할 수 없다.

프론트는 401 이후 반복 조회를 중지하고, 토큰 갱신 성공 후에만 다시 요청해야 한다. 비로그인은 로그인 전용 상태 API를 호출하지 않고 guest WS를 사용한다.

### HTTP 503: 18건

초대 알림 8건, 수신 설정 5건, 제재 조회 5건이다. 11건은 약 5.07~5.09초 뒤 실패했다. 인증 코드의 외부 토큰 조회가 `timeout=5`를 사용하므로 외부 인증 조회 타임아웃 가능성이 높다. 나머지 7건은 00:00:01~00:00:02에 0.07~0.10초 만에 집중 실패했다.

로그에는 503 응답의 `msg`나 해당 upstream 응답 상태가 없어 원인을 확정할 수 없다. 5초짜리 실패를 DB 과부하로 단정하거나 자정 실패를 운영 재시작으로 단정하지 않는다. 토큰을 기록하지 않고 AUTH_UNAVAILABLE/CHAT_DATABASE_UNAVAILABLE 등 오류 코드와 원인 분류를 남기면 이후 분석이 가능하다.

### 스캔 경고

`wp-admin`, PHP 파일, `.env` 등 탐색 요청이 있다. BLOCKED(path) 460건과 일반 access log의 404 등을 실제 서비스 사용자 오류와 구분한다. 전체 HTTP 반복 조회 건수와 비교하면 주요 트래픽 원인은 아니다.

## 우선 조치

1. **프론트 중복 REST polling 줄이기:** 정상 WS 연결 중에는 snapshot/event로 세 상태를 갱신한다. REST는 필요한 초기 조회·사용자 동작·WS 복구 실패 시에 사용하며 fallback polling에 중복 타이머와 무제한 재시도가 생기지 않게 한다.
2. **WS 연결 수명 확인:** 페이지/계정 모드별 연결을 재사용한다. React 재렌더·상태 변경·토큰 객체 변경 때문에 연결을 다시 만드는지 확인한다. 종료 코드와 재연결 사유를 토큰 없이 수집하고 backoff를 적용한다. 15분 재인증 외의 빈번한 재연결 원인은 프론트와 프록시에서 함께 확인한다.
3. **게스트 제한의 IP 기준 확인:** WS peer가 내부 프록시 주소로 기록된다. 게스트 연결 제한은 ASGI peer별 5연결/접속 20회·분 기준이므로 여러 사용자가 하나의 프록시 IP로 묶이면 서로 제한을 공유할 수 있다. 현재 시작 스크립트와 실제 프록시 신뢰 설정을 확인한다. 제한을 통째로 해제하거나 임의 헤더를 신뢰하는 방식으로 해결하지 않는다. 현재 로그에 종료 코드가 없어 이 현상의 실제 발생은 미확인이다.
4. **백엔드 종료 경쟁 오류 처리:** 위 전송 오류의 종료 처리와 정리 경로를 수정한다.
5. **내부 주기 조회 최적화:** 채팅은 연결별로 접속자 목록과 본인 상태를 각각 2초마다 DB 트랜잭션으로 조회한다. 이는 HTTP access log에 포함되지 않는다. 예를 들어 로그인 사용자 140명이 실제 동시 접속하면 두 조회만 약 140개 DB 트랜잭션/초가 발생하는 구조다. 접속자 목록의 공유 캐시·갱신 주기, 본인 상태의 이벤트 활용을 검토한다. 140명이 일간 사용자라는 사실만으로 이 수치를 운영 부하로 적용하지 않는다.
6. **OPTIONS 빈도 확인:** 캐시 헤더가 있더라도 왜 거의 매 polling에 preflight가 발생하는지 브라우저 Network와 CDN/프록시 응답으로 확인한다. 요청을 줄이는 조치부터 적용한다.

HTTP 응답이 빠르다는 이유로 WS/DB 부하가 없다고 결론 내리거나 worker/DB pool 크기를 먼저 늘리지 않는다. 먼저 반복 요청과 재연결의 원인을 줄이고 CPU·DB 연결/쿼리·Redis 지표를 함께 확인한다.
